# 020 — Two-Tool Release Pipeline (release-plz + cargo-dist)

## Context

The project has two distinct release concerns:

1. **Library publishing** — `workon` (the `git-workon-lib` crate) must be published to crates.io with correct version bumps and changelogs derived from conventional commits.
2. **Binary distribution** — `git-workon` (the CLI binary) must be distributed as pre-built binaries for four platforms, installable via a shell script and Homebrew.

No single Rust release tool handles both well. The previous setup used `release-please`, a language-agnostic tool that did not understand Cargo workspaces natively and required manual configuration to interact with crates.io at all.

A clean separation of responsibilities was needed, with a well-defined handoff point between the two concerns.

## Decision

Two tools own separate phases of the release pipeline:

**release-plz** (`release-plz.toml`, `.github/workflows/release-plz.yml`) owns versioning and publishing:
- Monitors `main` for new conventional commits.
- Maintains a release PR that proposes version bumps and changelog entries.
- On release PR merge: publishes crates to crates.io and creates a git tag.
- `git_tag_enable = true` — release-plz creates the version tag.
- `git_release_enable = false` — release-plz does NOT create a GitHub Release. This is the load-bearing boundary that prevents conflicts with cargo-dist.

**cargo-dist** (`dist-workspace.toml`, `.github/workflows/release.yml`) owns binary distribution:
- Triggered by any git tag matching the version pattern (`**[0-9]+.[0-9]+.[0-9]+*`).
- Builds binaries for four targets: `aarch64-apple-darwin`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`.
- Generates shell and Homebrew installers.
- Creates the GitHub Release with generated release notes.
- Publishes the Homebrew formula to `lettertwo/homebrew-tap`.
- Builds with `features = ["vendored"]` to produce portable, statically-linked binaries.

The handoff is tag-based: release-plz pushes a tag → cargo-dist's workflow triggers on that tag.

## Consequences

- Clean separation: release-plz never touches GitHub Releases; cargo-dist never touches crates.io.
- The tag-based handoff is simple and reliable — no shared state or coordination required.
- Two config files to maintain (`release-plz.toml`, `dist-workspace.toml`), but each is small and focused.
- The `git_release_enable = false` setting in `release-plz.toml` is critical — removing it would cause release-plz and cargo-dist to both attempt to create a GitHub Release for the same tag, resulting in a conflict.
- cargo-dist's workflow also runs on pull requests (in plan-only mode) to validate release configuration without publishing.
- The `vendored` feature bundles OpenSSL and other native dependencies into the binary, ensuring the distributed artifacts work without system library requirements.

## Version Coupling

`git-workon` and `git-workon-lib` share a `version_group = "main"` in `release-plz.toml`. release-plz assigns both crates the highest of their independently-calculated next versions, so a breaking change in the lib automatically major-bumps the CLI even when the breaking commit only touches lib files.

**Rationale:** The CLI is a thin wrapper over the lib's user-visible behavior. A `feat(lib)!:` commit is effectively a breaking CLI change from the user's perspective, so the CLI's semver should reflect it.

**Trade-off:** An internal lib refactor that triggers any bump will also bump the CLI even if no CLI behavior changed. This is accepted as an over-bump is harmless; an under-bump silently exposes users to a semver-broken dependency.

**Alternative considered:** A CI guard that fails the release PR when the lib major-bumps without the CLI major-bumping. Rejected in favor of the simpler automated mechanism.

`git-workon-fixture` is excluded from the version group — it has `publish = false` and is versioned independently.
